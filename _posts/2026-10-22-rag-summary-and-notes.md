> **一句话理解**  
> **RAG（Retrieval-Augmented Generation，检索增强生成）**是在模型回答前，从外部知识源检索相关证据，并把证据连同问题一起交给模型生成答案。它把 LLM 的参数知识与可更新、可追溯的外部知识结合起来。

> **最重要的认识**  
> RAG 不是“向量数据库 + LLM”的简单拼接，而是一条包含**资料摄入、索引、查询理解、召回、重排、上下文组装、生成、引用和评测**的完整信息系统。  
> RAG 可以降低幻觉，但不能自动消除幻觉；检索到错误资料时，生成模型仍可能自信地给出错误答案。

## 1. RAG 为什么出现

### 1.1 参数知识的局限

LLM 的知识主要存储在模型参数中，这种“参数记忆”存在几个问题：

- **知识有截止时间**：模型训练完成后，事实不会自动更新；
- **私有知识缺失**：企业文档、个人笔记和内部数据库通常不在训练数据中；
- **来源不透明**：模型可能回答正确，却难以指出具体证据；
- **修改成本高**：很难只删除或更新模型参数中的某一条知识；
- **容易幻觉**：模型会生成语言上合理但事实错误的内容。

### 1.2 RAG 的基本解决思路

RAG 把知识分成两部分：

| 知识类型 | 存储位置 | 特点 |
|---|---|---|
| 参数知识 | 模型权重 | 通用、压缩程度高，但更新困难 |
| 非参数知识 | 文档、数据库、搜索索引 | 可更新、可删除、可追溯 |

回答问题时，系统先访问非参数知识，再让模型基于检索证据生成答案。

### 1.3 概念来源

“Retrieval-Augmented Generation”这一名称来自 Lewis 等人在 2020 年发表的论文 [Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks](https://arxiv.org/abs/2005.11401)。

原始工作将：

- DPR 稠密检索器；
- Wikipedia 向量索引；
- 预训练 Seq2Seq 生成模型；

结合成可训练的系统，并提出两种形式：

- **RAG-Sequence**：整段输出共享同一组检索文档；
- **RAG-Token**：不同输出 token 可以依赖不同文档。

今天工程领域所说的 RAG 已经比原论文宽泛得多，通常泛指“外部检索 + 上下文增强 + 生成”的完整系统。

## 2. RAG 的核心概念

| 概念 | 含义 |
|---|---|
| Corpus | 可检索的全部资料集合 |
| Document | 一份完整资料，如 PDF、网页或数据库记录 |
| Chunk | 从文档切出的检索单元 |
| Metadata | 标题、来源、时间、权限、章节、产品等结构化信息 |
| Embedding | 把文本映射为稠密向量的模型 |
| Index | 支持快速检索的数据结构 |
| Retriever | 根据查询召回候选资料的模块 |
| Reranker | 对候选资料做更精细的相关性排序 |
| Context | 最终放入 LLM 输入窗口的证据 |
| Generator | 根据问题和证据生成答案的模型 |
| Grounding | 让答案受到外部证据约束 |
| Provenance | 答案或知识的来源与可追溯性 |

### 2.1 相关性不等于正确性

检索系统通常优化的是“查询与文档是否相关”，但一个文档即使相关，也可能：

- 已经过期；
- 与其他文档冲突；
- 只包含问题背景而不包含答案；
- 来自不可靠来源；
- 对当前用户没有访问权限。

因此，生产级 RAG 还需要考虑权威性、时效性、权限和证据充分性。

## 3. 标准 RAG 的完整流程

RAG 可以分成离线的**索引阶段**和在线的**查询阶段**。

```text
[ 原始文档 ] ──→ [ 离线索引：解析·切分·元数据·Embedding ] ──→ [( 混合索引 )]
                                                                   │
[ 用户问题 ] ──→ [ 在线检索：改写·召回·融合·重排 ] ◀───────────────┘
                                  │
                                  ▼
                 [ 上下文组装与 LLM 生成 ] ──→ [ 引用·验证·输出 ]
```

### 3.1 离线阶段

1. 获取原始资料；
2. 解析 PDF、网页、Office 文档或数据库；
3. 清理页眉、页脚、乱码和重复内容；
4. 按语义或结构切分；
5. 补充来源、标题、时间和权限等元数据；
6. 计算 Embedding；
7. 建立稠密、稀疏或图索引；
8. 保存原文和版本信息。

### 3.2 在线阶段

1. 接收用户问题；
2. 识别用户意图、实体和筛选条件；
3. 必要时改写或拆分查询；
4. 使用关键词、向量或图检索召回候选；
5. 合并、去重并重排；
6. 选择最终证据；
7. 组装 Prompt；
8. 让 LLM 基于证据作答；
9. 返回引用、置信提示或“不知道”；
10. 记录日志，用于后续评测。

## 4. 检索方法

### 4.1 稀疏检索：BM25

BM25 根据词项匹配、词频、逆文档频率和文档长度计算相关性。

适合：
- 产品编号、法规条款、缩写和专有名词；
- 人名、版本号、错误码；
- 用户问题与原文措辞接近的场景。

优点：
- 无需训练；
- 结果容易解释；
- 精确词匹配强；
- 是非常可靠的基线。

缺点：
- 不理解同义表达；
- 用户问题和文档用词不同时容易漏召回。

### 4.2 稠密检索：Embedding

稠密检索把查询和文档映射为向量，通过余弦相似度或点积寻找语义相近内容。

常见相似度：

$$
\operatorname{cos}(q,d)=\frac{q\cdot d}{\lVert q\rVert \lVert d\rVert}
$$

[Dense Passage Retrieval](https://arxiv.org/abs/2004.04906) 证明了双编码器稠密检索在开放域问答中的价值。

适合：
- 同义词和自然语言表达差异较大的问题；
- 概念检索；
- 用户问题较口语化的场景。

缺点：
- 可能忽略型号、数字和关键词；
- Embedding 模型与业务领域不匹配时效果不稳定；
- 单向量会压缩掉部分细粒度信息。

### 4.3 混合检索

混合检索同时使用 BM25 和 Embedding：

```text
关键词召回 ─┐
            ├→ 结果融合 (RRF) → 精排 (Rerank) → 组装上下文
向量召回 ───┘
```

它结合了稀疏检索的精确词匹配与稠密检索的语义泛化。常用融合算法是 Reciprocal Rank Fusion（RRF）：

$$
\operatorname{RRF}(d)=\sum_{r\in R}\frac{1}{k+\operatorname{rank}_r(d)}
$$

其中 $R$ 是不同检索器的排序列表，$k$ 是平滑常数。

[Anthropic 的 Contextual Retrieval 实验](https://www.anthropic.com/engineering/contextual-retrieval)也采用 Embedding、BM25、融合和 Rerank 的组合。具体收益依赖数据，不能直接把任何公开实验数值当成自己系统的保证。

### 4.4 Late Interaction 与 ColBERT

普通双编码器把整段文本压缩成单个向量。ColBERT 保留查询和文档的 token 级表示，再进行较轻量的 late interaction。

[ColBERT](https://arxiv.org/abs/2004.12832) 在表达能力和检索效率之间提供了另一种折中：
- 比单向量检索保留更多细粒度匹配；
- 比完整 Cross-Encoder 更适合大规模检索；
- 索引体积和系统复杂度通常更高。

### 4.5 元数据过滤

向量相似度不能替代业务条件。应把以下内容作为元数据过滤：
- 用户或租户权限；
- 产品、地区和语言；
- 文档类型；
- 生效时间；
- 版本与数据保密级别。

典型流程：**先按硬条件过滤 → 再计算相关性 → 最后重排**。

## 5. 文档切分与索引

### 5.1 为什么必须切分

整篇长文档直接做一个 Embedding 会丢失局部语义；切得过碎又会失去上下文。Chunking 的目标是让每个检索单元：
- 能表达一个相对完整的语义；
- 能独立判断是否与问题相关；
- 长度适合 Embedding 和 LLM 上下文；
- 能追溯到原始章节。

### 5.2 常见切分策略

| 方法 | 做法 | 适用场景 | 风险 |
|---|---|---|---|
| 固定长度 | 按字符或 token 切分 | 快速原型 | 容易切断语义 |
| 滑动窗口 | 固定长度并加入 overlap | 连续文本 | 重复内容较多 |
| 结构化切分 | 按标题、段落、列表和表格 | 文档结构清晰 | 需要可靠解析 |
| 语义切分 | 根据主题变化确定边界 | 长文章 | 计算成本高 |
| Parent-Child | 小块检索、返回大块上下文 | 需要细召回和完整语境 | 存储与映射更复杂 |
| Contextual Chunk | 给 chunk 补充文档级说明 | chunk 脱离原文后含义不清 | 摄入成本增加 |

### 5.3 Chunk 大小没有万能答案

影响 Chunk 大小的因素：
- 答案通常跨几句话还是跨多个章节；
- 文档是法规、论文、客服手册还是代码；
- Embedding 模型的输入长度；
- LLM 上下文预算；
- 是否使用 Parent-Child；
- 是否需要保留表格和列表。

工程上可以从数百 token 的结构化 chunk 开始，但最终必须用自己的查询集评测，而不能照抄固定数值。

### 5.4 Overlap 的作用与代价

Overlap 可以减少语义边界被切断的问题，但也会造成索引膨胀、结果高度重复以及上下文 token 浪费。更好的替代方案是按结构切分、构建父子关系或按需扩展相邻块。

### 5.5 为 Chunk 补充上下文 (Contextual Retrieval)

一个 chunk 可能只写着：“该产品在第二季度增长了 3%”。单独看无法知道是哪款产品、哪一年。可以在摄入阶段通过大模型为每个 chunk 生成补充说明：

> 来源：A 公司 2025 年度报告；章节：产品 X；时期：2025 年第二季度。

再将“上下文说明 + 原始 chunk”用于 Embedding 和关键词索引，大幅提升孤立文本的命中率。

## 6. 查询理解与检索增强

### 6.1 查询改写 (Query Rewrite)

用户在对话中提问往往带有代词与语境依赖（例如：“它今年还有这个政策吗？”）。改写模块结合对话历史消除指代、补齐实体，转化为独立的完整检索问题。

### 6.2 Multi-Query 与 Query Decomposition

- **Multi-Query**：生成同义但措辞不同的多个子查询并行召回，解决词项不匹配；
- **Query Decomposition**：将复杂的复合问题（如“对比 A 与 B 的定价并分析利润影响”）拆解为若干细分事实问题分别检索后再综合。

### 6.3 HyDE (假想文档检索)

[HyDE](https://arxiv.org/abs/2212.10496) 先让 LLM 根据问题生成一份“假想的完美回答文档”，再用这个假想文档的向量去检索真实资料。假想内容只用于检索锚点，绝不能直接充当事实答案。

### 6.4 智能路由 (Routing)

不同问题应分流到不同引擎：

| 问题类型 | 建议路径 |
|---|---|
| 闲聊或写作 | 直接调用 LLM |
| 私有知识问答 | 文档 RAG |
| 精确业务数据 | Text-to-SQL / API |
| 最新公开信息 | Web Search |
| 复杂关系与全局宏观主题 | GraphRAG |
| 高风险决策 | 检索 + 规则引擎 + 人工复核 |

## 7. 重排与上下文组装

### 7.1 为什么需要 Reranker

召回阶段追求“快”与“全”（召回 20~100 个候选）；重排阶段（Cross-Encoder 或专用重排模型）则追求“精”，深度计算查询与候选间的语义相关度，挑选出 Top-K（如 3~5 个）高质量切片输入大模型。

### 7.2 Lost in the Middle 现象

研究表明（[Lost in the Middle](https://arxiv.org/abs/2307.03172)），模型对输入上下文的头部和尾部信息敏感，位于长上下文中间的关键事实极易被忽略。因此：
- 盲目堆积超长上下文有害无益；
- 高度相关的关键证据应排在最前或最后；
- 严格控制最终上下文预算。

## 8. RAG 的主要类型

### 8.1 Naive RAG vs Advanced RAG

- **Naive RAG**：简单的 `Query -> Vector Search -> Top-K -> LLM`，脆弱且容易受分块质量与噪声影响；
- **Advanced / Modular RAG**：引入查询改写、混合检索、元数据过滤、重排、父子块映射与后验检查，是生产级系统标配。

### 8.2 Self-RAG 与 Corrective RAG (CRAG)

- **[Self-RAG](https://arxiv.org/abs/2310.11511)**：通过自省 Token 决定是否需要检索、所选材料是否相关、生成内容是否有依据；
- **[CRAG](https://arxiv.org/abs/2401.15884)**：增加检索质量评估器，根据置信度动态决定是采纳证据、补充网页搜索还是触发降级纠错。

### 8.3 GraphRAG (知识图谱增强)

由 Microsoft 提出的 [GraphRAG](https://microsoft.github.io/graphrag/) 借助实体抽取与社区聚类总结，专攻普通向量检索难以解决的**全局性、跨文档多跳关系汇总问题**（如“总结这家公司五年来所有的合规风险事件”）。

### 8.4 Agentic RAG

将 RAG 从被动的数据管道升级为智能体的**主动知识感知工具**：由 Agent 根据目标自主规划何时检索、拆分子任务、多次递归验证证据完整性。

## 9. RAG 评测与失败模式分析

### 9.1 分模块拆解评测（RAG 三元组）

切忌仅凭最终输出打整体分，必须将检索端与生成端彻底拆离：

1. **Context Relevance（检索相关性）**：召回的内容是否包含解答问题所需的事实；
2. **Groundedness / Faithfulness（证据忠实度）**：生成答案中的每一句话是否都能在检索证据中找到依据（严防幻觉）；
3. **Answer Relevance（答案切题度）**：生成内容是否真正解答了用户的初始诉求。

### 9.2 常见失败模式与速查

| 失败表现 | 根因排查 | 针对性解法 |
|---|---|---|
| **完全检索不到** | 关键词被向量压缩 / 措辞差异大 / 切块过大 | 引入 BM25 混合检索、Query 改写、缩小 Chunk |
| **检索到了排在后面** | 双编码器区分度不足 | 引入 Cross-Encoder 重排器、调整 RRF 权重 |
| **有正确证据但仍回答错误** | 证据被噪声掩盖 / 模型指令遵循弱 | 精简上下文、强化 Prompt“严格基于证据拒答”要求 |
| **虚假引用** | 模型强行编造来源 | 强制要求输出引用片段锚点，引入生成后正则比对 |

## 10. RAG 与 Fine-tuning、长上下文的技术选型

| 维度 | RAG | Fine-tuning (微调) | 长上下文 (Long Context) |
|---|---|---|---|
| **最擅长领域** | 动态外部知识、私有文件库 | 行为习惯、特定语气、领域格式规范 | 少量长文档的一次性深度推理 |
| **知识更新成本** | 毫秒/秒级（更新索引即可） | 极高（需重新训练与验证权重） | 每次调用均需传递完整上下文，费用高 |
| **事实可溯源性** | 极佳（可追溯精确页码与出处） | 极差（黑盒权重记忆） | 较好 |

> **核心法则**：  
> - 如果是**知识问题**（模型不知道事实）➔ 选 **RAG / 数据库查询**；  
> - 如果是**行为问题**（模型知道事实但说话口吻、输出 JSON 格式不对）➔ 选 **Prompt 调优 / Fine-tuning**。

## 11. 从零构建 RAG 的工程实现范例

```python
def answer(user, question):
    # 1. 结合对话历史完成查询改写
    standalone_query = rewrite_with_chat_history(question)

    # 2. 权限与元数据前置过滤（必须在检索前执行！）
    filters = {
        "tenant_id": user.tenant_id,
        "allowed_groups": user.groups,
        "effective_at": now(),
    }

    # 3. 混合多路召回
    dense_hits = dense_search(standalone_query, filters, top_k=40)
    sparse_hits = bm25_search(standalone_query, filters, top_k=40)

    # 4. 倒数排名融合 (RRF) 与精排 (Rerank)
    candidates = reciprocal_rank_fusion(dense_hits, sparse_hits)
    ranked = rerank(standalone_query, candidates)
    
    # 5. 上下文预算控制与组装
    evidence = build_context(ranked, token_budget=6000)

    # 6. 证据不足时主动拒答，不强行幻觉
    if evidence_is_insufficient(evidence):
        return answer_with_abstention()

    # 7. 基于证据生成受约束答案
    response = generate_grounded_answer(
        question=question,
        evidence=evidence,
        require_citations=True,
    )

    return verify_and_return(response, evidence)
```

---

## 12. 总结

RAG 的核心不是“让模型读更多文本”，而是在**合适的时间把必要、可信、最小集的证据呈现在模型面前**。

构建健壮的生产级 RAG，本质是一场精细化的信息检索与系统工程实践。从可测量的基线出发，逐步迭代分块、召回、重排与抗注入防护，才能真正让大语言模型落地为可靠的企业级生产力。
